## The Target Runtime Architecture

The final deployed system must have the following logical form:

```text
base policy executes
        |
        v
confirmed failure supplied externally
        |
        v
generate executable recovery proposals
        |
        v
predict compact factorized consequences for each proposal
        |
        v
select exactly one local recovery OR select fallback/replan
        |
        v
execute only the selected choice
        |
        v
re-observe the real post-action state
        |
        +---- recovered / valid handoff -> base policy resumes or replans
        |
        +---- still locally recoverable -> generate/select another recovery
        |
        +---- local recovery not trustworthy -> safe fallback + base-policy replanning
```

At deployment time, unexecuted recovery proposals must remain counterfactual. The system may not execute all proposals online and then retroactively select the best one.

Executing all proposals from a restored simulator checkpoint is allowed only for offline data generation, oracle coverage analysis, and post-selection scientific evaluation.

# EXP_F1 — Mandatory First Scientific Experiment

## EXP_F1 Title

**Confirmed-Failure Benchmark and Recovery-Proposal Coverage Reconstruction**

`EXP_F1` is the new campaign's first real experiment. It must not be an audit-only experiment.

The purpose of `EXP_F1` is to remove the old trigger problem completely and answer the first two questions required by the research charter:

> **Can we construct reproducible confirmed-failure checkpoints with deployment-consistent controller state, and from those exact states, how much local recovery headroom exists under several materially different executable recovery-proposal families versus fallback/replanning?**

## EXP_F1 Required Phase: Exact Failure and Handoff Semantics

Before collecting the formal dataset, inspect the runnable simulator/environment/controller implementation and extract the exact machine semantics of:

```text
base-policy execution
confirmed task failure or failure event
success
unsafe/invalid state if such a predicate exists
base-policy action queues
controller memory/state
policy hidden or cached state if present
state checkpoint and restoration
fresh replanning
post-recovery continuation
safe disengagement / fallback
```

This inspection is infrastructure inside `EXP_F1`; it does not complete `EXP_F1`.

Choose and document one primary post-recovery control semantics for the new benchmark. If the base policy supports a true fresh replan from current observation, prefer a clearly defined fresh-replanning protocol because it removes ambiguous stale pending actions. If that choice is not valid for the actual controller, use the exact controller-supported semantics and document it.

Do not guess which semantics exist. Read and run the implementation.

## EXP_F1 Required Phase: Generate Fresh Confirmed Failures

Run new base-policy executions and capture fresh failure checkpoints at the **first exact machine-verifiable point where the benchmark/controller defines the execution as failed**, not at an inferred earlier “likely failure” state.

Use genuinely independent task executions, demonstrations/initial conditions, and manipulation mechanisms supported by the current simulator. Reuse the broad manipulation-mechanism inventory from prior work only after verifying the exact runnable task IDs from code and manifests.

Do not merely restore the old P31–P35 states and call that new data. Historical states may be used for debugging and comparison, but `EXP_F1` must generate new executed failure evidence.

For every saved checkpoint, verify restoration reproducibility. If restoration changes the base-policy continuation or physical state materially, repair checkpointing inside `EXP_F1` before formal measurements.

The formal benchmark should contain enough diversity to distinguish task-specific artifacts from a general recovery problem. Use as many genuinely different mechanisms as the already runnable environment supports, with multiple independent failure instances per mechanism. Do not create cosmetic variants only to increase the task count.

## EXP_F1 Required Phase: Build Multiple Recovery Proposal Families

From each exact confirmed failure state, instantiate and actually execute several **materially different** recovery-proposal families.

The first family may reuse verified existing heterogeneous recovery actions from prior EXP_G/EXP_P code, but their implementation semantics must be read from code rather than inferred from names.

In the same EXP, attempt at least two materially different proposal-generation mechanisms justified by the current repository and literature. Examples include:

```text
retrieved corrective trajectory segments from successful/recovery data
task-space corrective skills or waypoint controllers
recovery subgoals / familiar-state milestones executed by a frozen policy
state-conditioned short corrective chunks
short model-predictive / optimization-based local plans
learned local feedback recovery policy trained only from development recovery data
```

Choose mechanisms that are actually implementable for the exact simulator/controller. Do not force all examples if the task interface makes them nonsensical. The requirement is scientific diversity, not checking boxes.

If implementing a proposal family requires missing instrumentation or data, solve that infrastructure problem inside `EXP_F1` and execute the family before declaring the experiment complete, unless valid evidence from an earlier subrun demonstrates that the family is physically inapplicable to the interface. In that case, replace it within `EXP_F1` with another materially different executable family.

## EXP_F1 Required Phase: Explicit Fallback Baseline

Implement the benchmark's valid fallback/replanning path.

Fallback must be based on the actual current world state. It must not silently reset object states or restore the episode unless the benchmark explicitly declares an environment reset condition.

Measure what happens when the system abandons local recovery and invokes the base-policy replanning path from the confirmed failure state or after a safe disengagement step, according to the exact controller semantics.

This fallback outcome is part of the benchmark and later decision space.

## EXP_F1 Required Phase: Oracle Coverage Matrix

For scientific evaluation only, restore each confirmed failure checkpoint repeatedly and execute every legal local recovery proposal under identical semantics.

For each execution, record the actual post-recovery state and the exact downstream handoff/replanning outcome needed to label whether the proposal produced a useful local recovery, harmful/unsafe result, failed recovery, or another exact outcome supported by the implementation.

This produces an evaluator-only recovery outcome matrix. It must never be available to the deployed selector before action selection in later experiments.

Compute and report at least the following conceptual decompositions using exact implemented metric definitions:

```text
fraction of confirmed failures with at least one valid local recovery
fraction with multiple valid local recoveries
fraction with no valid local recovery but fallback/replan succeeds
fraction with neither current local recovery nor fallback success under the defined protocol
marginal coverage added by each proposal family
proposal-family overlap and complementarity
harmful/unsafe outcome support
how recoverability varies across physical task mechanisms
```

This is the first clean estimate of **oracle local-recovery coverage** for the new confirmed-failure formulation.

## EXP_F1 Required Scientific Comparisons

`EXP_F1` should distinguish at least these explanations:

```text
A. The old recovery problem mainly failed because the fixed proposal set lacked coverage.
B. The old proposal families already contain broad recovery headroom, so selection/consequence modeling is now the dominant problem.
C. No single family is broad, but heterogeneous proposal families are complementary.
D. Many confirmed failures are genuinely not locally recoverable and require fallback/replanning.
E. Apparent recovery success changes materially with handoff/replanning semantics, proving that the label interface must be rebuilt before training the new selector.
```

Run enough actual interventions to determine which explanation is supported.

# Research Priority After EXP_F1

The campaign must follow the governing dependency order unless actual evidence proves that two stages can validly be combined.

## Priority A — Confirmed-Failure Benchmark

This is solved only when:

```text
failure is already established before the recovery method starts
checkpoints are reproducible
controller/handoff semantics are explicit
matched interventions can start from the same state
new independent failure instances exist
both locally recoverable and fallback-relevant failures are represented
```

Do not return to trigger research after this is solved.

## Priority B — Recovery Proposal Coverage

If oracle coverage is insufficient, broaden the proposal generator using new families, not endless tuning of the same route library.

Useful directions may include retrieval, subgoals/milestones, task-space skills, local feedback policies, short planning, or combinations supported by current evidence.

Every improvement must report marginal oracle coverage and family complementarity so proposal-generation gains are not credited to consequence prediction.

The proposal generator is a modular substrate, not the central novelty.

## Priority C — Deployment-Consistent Consequence Interface

Once there is meaningful proposal headroom, rebuild consequence labels around the exact online causal sequence.

The label object must include the deployed recovery duration, actual resulting observation/state, exact handoff/replanning semantics, and task/safety consequences.

Start from factors justified by previous evidence, especially success-related and unsafe consequence. Test handoff/continuation consequence as a high-priority hypothesis because previous P-stage evidence showed outcome sensitivity to handoff semantics.

Do not add factors merely because they sound intuitive. Add a factor only if data show a distinct decision need.

## Priority D — Prove Factorization Is Meaningful

This is a mandatory paper requirement.

Compare factorized consequence representations against matched alternatives such as:

```text
one scalar success/value/verifier
direct state+proposal selector
success-only prediction
unsafe-only filter where meaningful
route/proposal-prior or retrieval-only control
factorized representation with factors removed or merged
shared representation + multiple heads
partially separated factor encoders if motivated
multiple downstream decision rules consuming the same frozen factors
```

The goal is to determine whether factorization provides a real representation/control advantage rather than merely more parameters.

Test mechanisms such as:

```text
cross-task generalization
cross-demonstration generalization
cross-proposal-family generalization
OOD proposal composition
unsafe/harmful selection
abstention/fallback calibration
regret relative to available oracle recovery headroom
factor-specific intervention/ablation
whether factorization permits useful risk constraints or Pareto decisions
```

If a matched scalar or direct selector is equally strong everywhere, report it and narrow the claim. Do not force factorization to be necessary if the data reject that claim.

## Priority E — Selector Generalization

The learned system must operate on unseen confirmed-failure states.

Use development, calibration, and untouched held cohorts with grouping that respects demonstrations/tasks/episodes.

Do not repeatedly open the final confirmation cohort.

Separate:

```text
no viable proposal
wrong consequence prediction
wrong decision rule despite adequate prediction
wrong fallback decision
execution mismatch
handoff mismatch
base-policy failure after successful local recovery
```

This decomposition is mandatory because aggregate task success cannot explain the mechanism.

## Priority F — Complete Closed Loop

The final system must execute:

```text
confirmed failure
-> proposal generation
-> pre-execution factorized consequence prediction
-> select one local recovery or fallback
-> execute selected choice only
-> real re-observation
-> repeat recovery if justified
-> fallback/replan when local recovery is not justified
-> return to base policy after valid recovery
-> final task outcome
```

Include selected-only evidence. Log every recovery cycle. Do not use evaluator oracle outcomes online.

Compare one-shot versus repeated re-observation when scientifically meaningful. Test whether explicit fallback prevents harmful forced recovery. Test whether handoff logic is necessary for final success.

# Data and Leakage Discipline

No deployed feature may depend on the future outcome of a recovery proposal that has not yet been executed.

Offline outcome labels may be used for training and evaluator-only oracle analysis, but at deployment the system receives only information that would truly be available before selecting the action.

When same-state branching is used, verify restoration and determinism with matched-zero/equivalent controls supported by the simulator.

Do not count many proposal outcomes from one restored checkpoint as independent failure episodes.

Respect clustering by demonstration, episode, task, checkpoint, session, or other dependency structure in uncertainty analysis.

Maintain explicit manifests identifying development, calibration, held evaluation, consumed confirmation, and untouched final confirmation data.
